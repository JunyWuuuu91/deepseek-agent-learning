---
title: "上下文窗口是一块缓存"
description: "文章把注入叫 Inline，把放在窗外的全文叫 Spill。原型用截断的卡片和可分页的资源 id 做了对应的事。"
---

窗口是有限的。文章借用编译和系统设计的两个操作：

- Inline：马上可能用到的信息直接放进窗口，省掉一轮工具调用。
- Spill：超预算或不常用的全文留在外面，窗口里只留摘要或指针。

再加上局部性：先给对象 id 和摘要，再给邻近的一点内容，例如正文前 50 个字符、周围的聊天、评审里相邻的评论。超长的部分截断，并留下还能读下去的指针。

路由层还有一个专门的问题：很多后续事件已经直达工人，旧任务又不断堆积，窗口里放不下全部历史。文章把「沿 id 一跳一跳读回来」叫做 Chain of Recall。对象是触发、线程、工人会话。读回的结果本身也遵守 Inline 和 Spill，于是模型可以从当前消息走到线程，再走到相关工人，再走到另一条评审。

原型没有在 000 到 008 里使用 Inline、Spill、Chain of Recall 这几个英文名字。它做的是同一类预算控制，数字写在 007：

- 评估上下文里的触发文本最多 4000 字符。线程窗口是开头 5 条，加上触发两侧各 5 条。普通消息大约 400 字符，紧邻的两条可以到 1200。其余消息是 50 字符的预览，要用 `orchestrator_eval_read` 按 id 展开。
- 工人收到的第一条任务最多 1500 字符，后续输入卡片大约 600 字符。更长的内容带 `chars` 和读取指针。
- 资源页默认 4000 个 UTF-16 码元，最多 8000；列表默认 20 条，最多 50。执行器只能读自己的工单和到达过它的触发。

007 还写了一句和缓存直接相关的提示词顺序：策略段放在系统提示最后，这样策略变化时，前面的前缀可以保持不动。

长期记忆是另一件事。文章把「几个月之后」的记忆列为扩展瓶颈。原型的 007 写明：触发、决定、已结束工单和每次保存的设置版本目前都不会删除，会一直增长。那是存储增长，不是一份会遗忘、会更新的长期记忆。

## 练习

1. 选一条超过 600 字的评审评论，按原型的规则写出窗口里会留下什么、指针指向哪里。
2. 解释为什么策略段放在提示词最后对缓存有利。对照 DeepSeek 的前缀缓存：命中要求整段前缀一致。
3. 在术语上把「文章的 Chain of Recall」和「原型的 resource id」并列写出来，不要把后者说成文章里的那个专有名字已经写进了代码注释。
